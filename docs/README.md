# dsh-plugin-pstd

> 插件命名铁门 N1–N8 与 R006 十项审查员（含 P1–P5 模式化交付生成）· 常驻插件包形态

本包是 PSTD 系列标准的**常驻执行体**：把原本只存在于会话内动态插件（进程重启即消失）的命名门、R006 十项审查员、
模式化交付生成器落到盘上，随 profile 启动常驻。规范正文的落盘镜像见
`~/dsh-collab/rules-registry/naming-standard-N1-N8-v1.md`（附独立复核器 `verify-naming-standard.py`）。

## 为什么需要（事故/证据）

1. **R006 事故表首行**：插件缺 `type: module` → CLD 启动崩溃。本包 `package.json` 必有 `type: module`。
2. **「九项全绿却根本挂不上」**：第一版参考实现的 `defineTool` 嵌套 object 缺 `additionalProperties` →
   `UNSUPPORTED_SCHEMA` → `apply()` 阶段崩，交付物在运行时不存在。本包所有输出 schema 用 `{ type: "json" }` 免嵌套陷阱，
   且 `--selfcheck` 会**真挂载一次并断言注册到的 5 个工具名**。
3. **命名漂移的实据**：全机审计发现 `dsh-plugin-agent-bus` 的 `package.json name` 仍是 `dsh-plugin-agent-way`、
   `cordis.patch.yml` 的 `name` 也没改；`files` / `md-preview` / `ui-spec` 的包名与目录名不一致；
   `devices/` 下 4 个 `dsh-plugin-cldvoice.bak-*` 目录含点号且超长（点号会破坏目录枚举与黑板键）。
4. **判据必须来自实测面而非声明面**：本包的「16 条负例」错误数字曾从工具描述传到交付卡、再传进 R047 账本，
   而运行时输出一直是 15。v1.0.2 起描述不再写死任何条数。

## 用法与退出码

```
node cli.js --help            # 自解释用法
node cli.js --selfcheck       # ① 能力清单 ② 不该发生路径 ③ 依赖完整性 + 真挂载冒烟（三态）
node cli.js --lean4-check     # 约束门六项 A–F 自证
node cli.js --tool-version    # 版本（唯一来源 package.json）
node cli.js --dry-run         # 只读状态报告，零变更
node cli.js --json            # 机器可读输出（与上面任意旗标并用）
```

退出码：`0` 成功 · `1` 失败/门失效 · `2` 用法或 IO 错误（未知旗标一律 `2`）。

## 已知边界（不粉饰）

1. **profile 挂载行不在本包内**：`cordis.patch.yml` 已就位（`id: pstd` / `name: dsh-plugin-pstd`），但把本包挂进
   `~/.dsh/profiles/**` 是另一个步骤，本包不自我挂载。
2. **与动态版同名工具的冲突**：动态版 PSTD（会话内 `pstd-2`）与本包注册**同名** 5 个工具。
   两者同时活着时工具名会撞车 —— 落盘常驻生效前应先停掉动态版。
3. **⑧ 落链不代查**：本包无网络能力，登记卡是否 200 需人工/其它工具回读确认（审查结果里如实标为未实测）。
4. **「登记」未被本门约束**：命名门只拦 `plugin_pattern_scaffold` 的写盘路径；黑板登记卡（`bb_card_send`）没有前置校验，
   不合规的名字仍可被登记。这是 R047 的已知缺口，本包未声称已解决。
5. **豁免无结构化表达**：本包没有 `exemption` 字段，豁免只能在 `package.json` 的 `r006` 段或账本里显式声明。
6. **跨设备执行面只在本机**：`resolveBase` 探测本机 `workspaceRoot`/`~` 与 `~/dsh-collab/devices`；N4 唯一性查本机活体工具表。
   跨设备需各设备各自运行或分发本包。
7. **A–F 的 A/D/F 是文本级证明**：A 扫源码、D 验调用点顺序、F 数调用点，都基于源码文本（已剥离注释/字符串/正则），
   不是形式化证明；`--lean4-check` 会把方法与数字一并打印出来供复核。
8. **★★ `plugin_name_gate action=audit` 只审 N1–N4，不审 N5–N8 —— 且旧输出未声明这一点**（本版修正披露，2026-10-08）：
   audit 的 `violationsByRule` 只可能出现 N1/N2/N3（目录级）+ 每条的 N4（工具名），**N5 日志路径 / N6 登记卡键 / N7 版本单一来源 / N8 保留字从未出现在输出里**；
   而输出给出 `pass/fail` 计数，**读者极易把绿灯读成「N1–N8 全过」**。这是典型的「**未检查 ≠ 通过**」（R006 坑#3 的形态）。
   **实测代价（**观测面必须写清**——作者首次报数时漏了这一点，被裁判指出后用显式观测面复算；本条即「计数必须附观测面」的自我适用）**：
   · **观面A**（作者首报，仅扫插件目录内 `.js`/`.mjs`）：声明 5 / 合规 3 / 违规 **2** —— **低估**；
   · **观面B**（裁判判据：两扫描根全递归、**不限文件类型**，匹配 `logs/<name>.log`）：声明 **15** / 合规 **7** / 违规 **8**，与裁判实测**逐个相符**。
   · 8 个违规者：`assert-audit`、`cldvoice-activate`、`agent-bus`、`bb-card-send`、`bus-queue-triage`、`drift-scan`、`launchd-scan`、`wargame-sim` —— **8/8 均写成 `<slug>.log`、缺 `dsh-plugin-` 前缀**（agent-bus 另写成 `agentway-relaunch.log`）⇒ 是**系统性**违规而非零星。
   对 bb-card-send 跑 audit 时它报了 N3 ✓，却**漏掉真实的 N5 违规**（该条在观面A、B 下均成立）。
   **第二个缺口（裁判发现，作者未察）**：audit 的 `pass: 30` **把 `partial` 计入了**。44 = pass 30 + fail 14，而 verdict=partial 的条目有 **11** 个 ⇒ 30 − 11 = **19** 才是四项全 pass。**「未验证」被并进「通过」的计数** —— 与本条边界同一病，且就在同一工具的输出里（算术可自证：11 个 partial 既不在 fail 中，则必在 pass 中）。
    **（语义前提：`partial` 与 `fail` 互斥 —— 下列算术依赖它）**：若日后引入「既 fail 又部分未验」的复合状态，此算术会**静默失效**，故在此显式声明。

   **另一处精确化（裁判）**：`violationsByRule` 只有 N1/N2/N3 三个键，**N4 也不进**（它只以逐条目形式出现），N5–N8 **连条目都没有**。
   **当前处置**：本版**只修正披露**（不声称已覆盖），audit 的 N5–N8 覆盖按版本纪律排入下一版（1.0.5，待 1.0.4 重启验收完毕再动包）。
   **1.0.5 待办（三条，均由裁判提出）**：① audit 出**分项计数**（N1–N8 各自 pass/fail/unverified/skipped），不用单一 `pass/fail`；② `partial` **不并入** `pass`，或至少单列；③ 把「audit 只审 N1–N4」做成一行**机器可读的未测面**（与 R046 v1.1.4 的 `surface_unmeasured` 同构）。
   **使用约束（请照此读 audit）**：audit 绿灯**只**意味着 N1–N4 通过；N5–N8 必须另判（N7 见 `plugin_review` R6、N5/N6/N8 目前无自动判据）。

## 坑（都踩过）

1. **门太宽**：把合法键也当违规 → 先精确白名单命中，再对非白名单输入判禁用词。实测代价：全机审计曾 43/43 全误报。
2. **扫描器误伤自己**：扫源码前先剥注释/字符串/正则字面量，否则自己的检测正则会被当靶子。
3. **空洞通过**：剥离字面量后读不到实参 → 调用点枚举为 0 → 「0 ⊆ 允许」假通过。本包 F 项因此要求**恰好 1 处**调用点。
4. **假失败**：依赖解析不到就说插件挂不上 —— 应先分辨「环境问题」与「包问题」（缺 node、peer 解析失败都走 `skipped`）。
5. **两处版本**：`const VERSION` 与 package.json 各写一份必然漂移，只留 package.json。
6. **返回值带 undefined**：`{ key: undefined }` 会被 harness 的 lossless-JSON 校验拒，切片动作会整片失效 —— 按需装配 payload。
7. **自递归**：`apply` 调 `runSelfCheck`、冒烟又调 `apply` → 依赖可解析时无限递归。必须有递归闸。
8. **判据过宽会砍到自己人（第三次）**：自扫原语曾用 `\b(exec|spawn|fork)\s*\(`，它命中 `RegExp.prototype.exec(`
   （如 `/SMOKE:.../.exec(stdout)`、`re.exec(text)`）—— 那是正则匹配不是进程执行，A 项因此误报 6 处。
   进程执行的真信号是 `child_process` 模块名与 `*Sync` 变体。自扫表必须**精确**（零假阳性），审查别人的可疑表才允许宽。
9. **`process.exit` 不该计入约束门红灯**：⑨ 明确要求固定退出码语义，Node 里就是 `process.exit(code)`；
   把它当危险原语会让**任何合规 CLI 永远拿不到 R10 绿灯**。R10 现已把它单独归类并显式标注
   「失败也 exit 0」这件事文本判不出、需人工确认。
10. **模块作用域的 execute 闭包抓不到 ctx**：把工具定义写在模块顶层、而 `execute` 里用 `apply(ctx)` 的参数，
    会「注册成功但一调用就 ReferenceError」。**挂载冒烟只证明注册成功，不证明可调用** —— 这类缺陷必须靠
    真调一次 execute 的宿主路径探针才发现。现改为 `createDefinitions(ctx)` 工厂。
11. **★ 声明面代替实测面（本包作者犯过）**：把工具描述里的「16 条负例」当成实测数据写进交付卡，账本照抄入 R047；
    运行时 selfproof 实际一直是 15。**描述里的数字不是证据**，条数一律由运行时矩阵算出、报数一律取运行时输出。
12. **★ 代理量代替实测量（本包作者犯过，与第 11 条同源）**：核对 profile 挂载时，我用「deps 只 +1」这个**代理量**
    推出「那 5 项 bundle 在 dependencies 里没有对应条目」并当成实测报出；逐项实测为假（5/5 都在 deps），
    真异常其实只有 2 项。**要从代理量下结论，就先做一次逐项取数**；否则报出去的是推论，而不是事实。
    （同日同一根源犯两次：一次以声明代实测，一次以代理量代实测。）
13. **★ 会撒谎的检查（三条实证）**：① CLI 末尾 `process.exit` 会把后台未完成的异步递归链**连带杀掉**，
    于是 `--selfcheck` 显示 pass —— 掩盖了真实的无界递归；② peer 解析失败会让真挂载冒烟静默走 `skipped`，
    看上去「没报错」；③ 指纹等价性只能证明「移植忠实」，**无法证明被移植的东西本身是对的** ——
    忠实移植了一个忠实移植的缺陷。凡「检查通过」都要先问一句：**它是怎么通过的？有没有一条路径让它必然通过？**

14. **★ 把绿灯当成「检查有效」（本包作者犯过 · 2026-10-08）**：电力故障后体检，我读到 `C1 marker=clean` 与
    `cleanExit=false` 并存，就把 `marker=clean` 读成「看门狗在正常工作」—— **反了**：两者自相矛盾正说明 `marker` 是
    **假绿**，判别依据只有 `cleanExit=false` 那一个字段。**采信任何绿灯前先问：它能红吗？**
    一个**恒绿**的检查不是检查，是装饰 —— 它把「没人发现异常」伪装成「没有异常」，比没有检查更危险。
    （本条由作者自己在电力故障后的体检中踩到，被协调者当场纠正；该样本已被其登记为 G9「假绿缺陷」的活体佐证。）

15. **★ 引用自检三问（本包作者犯过 · 2026-10-08，同一日三次）**：三次失手**全部落在「引用/标注」面、无一在推理面** ——
    ① 引登记卡「v14」而实测为 **15**；② 仓名缩成 `pstd` 而真名 `dsh-plugin-pstd`（缩写名端点实测 404）；③ 规模数未标读数时刻与口径。
    推理对了而指针错了，第三个人**仍然复跑不了** —— 引用精确性是**证据可重跑的唯一入口**。故引任何版本/名字/数之前，先过三问：
    **① 引的版本号是当前版本吗（引前现测）？② 引的名字/路径是全名吗？③ 引的数标了读数时刻吗？** 缺一即不得作为他人不可逆决策的输入。
    ⇒ **★ 升级（裁判 · 2026-10-08）**：**关键词检索不构成存在性判据（双向都不可靠）** —— 「未命中 ≠ 不存在」（假否定）与「命中 ≠ 存在」（假肯定）是同一个病的两面。⇒ **且「命中」之后还要再问一句「它是以什么用法出现的」**（引文 / 元讨论 / 标签用法）—— **「命中」不等于「按该用法在用」**。⇒ 这正是 pit 22 三分法的**适用前提**：**先分类，才能判要不要改**。
    ⇒ **★★ 三命题集合（裁判补全 · 2026-10-08）**：「关键词检索不可作判据」的**完整形式**是**三条**，前两条只在「**有 / 无**」轴上，第三条把轴扩到「**怎么在用**」：
      　① **命中 ≠ 有**（词出现 ≠ 对象存在）；② **未命中 ≠ 不存在**（词不出现 ≠ 对象不存在）；③ **命中 ≠ 按该用法在用**（词出现 ≠ 它被当作那个意思在用）。
      ⇒ **为何③不是锦上添花**：**没有③，pit 22 的三分法（引文/元讨论/标签）实际没有适用前提** —— 你必须先能回答「这个命中属于哪一类」，否则**删改无从下手**。⇒ **三者合起来才是完整的判据**。归属：①③ 的实例双方各有，**③ 的命句归作者**。
    **④ 引的位置稳定吗？**（行号/编号会漂，**与版本号无关**——实测同一 v1.5 下 §6 起始行号 20 分钟内为 204/196/205/212）：**交叉引用一律用「内容标题 + 行内唯一片段」**，非给行号不可时连同 **版本 + mtime + 内容片段** 一起给。

20. **★ 机制句不得用与证据同名的量词缩写（「简称把证据说成了原因」）**（裁判归档 · 2026-10-08；作者亦有同类实例，且落在本会话最常用的那个词上）：
    - **裁判的原例**：其机制句写「两板收敛有 **1–2 秒抖动**」（指**收敛时序**），而证据是「两板 **ts** 差 1 秒」—— **两者共用同一个量「1–2 秒」**。它后来用简称「**ts 抖动机制**」自我撤回时，就把**证据**说成了**原因** ⇒ **先造出一个从未主张过的东西，再认领它**。
    - **★ 作者的同类实例（本会话最常用的那个词）**：全场把该缺陷称为「**假红**」。但本会话自己的结论是：**断言在其时刻是对的**（两板 `value` 确实**瞬时不等**），只是**事后**回读时卡已落盘。⇒ 「假红」这个简称**把「事后已落盘」这个证据，说成了「断言错了」这个结论**。更准的说法是「**瞬时不一致 + 事后已落盘**」；要修的是**错误文案分级与退避重试**，**不是断言的真值**。
    - **危害**：**后续读者（包括原作者自己）会按简称去认领或撤回，从而产生虚假的账目变动**。
    - **⇒ 操作规则**：**机制句必须指名对象**，**不得使用与证据同名的量词缩写** —— 写「两板**收敛时序**抖动」而非「抖动」；写「**`value` 瞬时不等**」而非「不一致」；写「**瞬时不一致 + 事后已落盘**」而非「假红」。

21. **★ 状态码语义表（误读与处置顺序）**（表由裁判归纳 · 2026-10-08；`200` 行与「分离规则」由作者补）：
    | 码 | 语义 | 常见误读 |
    |---|---|---|
    | 400 | 请求非法（键/参数写法错） | 误当「不存在」 |
    | **401** | 认证失败 ⇐ **常是拿错凭据** | 误当「无权限」 |
    | 404 | 格式合法但不存在 | 误当「非法」 |
    | 409 | 冲突（如空仓返回 `Git Repository is empty`） | 误当「路径错」 |
    | **200** | **成功 ≠ 有信息**：可能是**体判据**（`branches` → 200 + body `[]`） | 误当「内容存在」 |
    - **本会话两处 401 方向相反**（作者均已复现）：复核员**该带黑板 token 却没带**（直 PUT 中枢板）；作者**带了错的凭据**（用黑板 token 访 GitHub API）⇒ **401 常常不是「无权」而是「凭据张冠李戴」** ⇒ **处置顺序：先问「我刚才是用哪个凭据发的」，再问「我有没有权限」** —— 否则会去查一个不存在的问题。
    - **★ 分离规则（作者补）**：**「判据是状态码还是 body」必须与码语义分开写** —— 同一事实在 `commits` 是**状态码判据**（409），在 `branches` 是**体判据**（200 + `[]`）⇒ 只写码语义会让人以为码总是判据。
    - **★ 完整的一层（裁判补 · 2026-10-08）**：`200` 行只写了「成功 ≠ 有信息」，需配它的兄弟条 —— 「**失败 ≠ 无结果**」（401 / 409 都是「**没做成，但告知你为何**」）。⇒ 两句合起来，「码」与「体」各自该看什么才完整。⇒ 并定下**写作顺序**：写判据时**先写「看码还是看 body」**，再写「码/体各自什么意思」—— 否则会像 `git rc` 那样，**用码去回答一个只有体能回答的问题**。
    - **★ 同码 message 措辞可能不一**：`commits`/`git/refs` = `Git Repository is empty.`，而 `contents` = `This repository is empty.` ⇒ **判定要落在 message 的语义，不能钉死某个固定串**。

      |---|---|---|---|
      | **可改载体**（卡 / 文档 / 手册） | 保留（**不得改字**） | 保留 | ★ **必须改** |

24. **★ 替代关系声明（修正了旧建议，必须声明哪部分被替代、以哪份为准）**（纪律句归裁判 · 2026-10-08；实例归作者）：

    ⇒ **★★★ 完整机制（裁判补出关键一层 · 2026-10-08）**：
      ・**代码事实**：`lib/core.js` **L90–L97 是纯同步代码**（比较、`if`、`logLine`，**无 await**）⇒ **只要 L89（循环）跑完，就必然执行到 `logLine`** ⇒ 所以「**日志里没有**」**反证「循环没有跑完」**（而不是「跑完了但没记」）。

## ★ 在役版本判据与「不可逆」的精确成本（2026-10-08 · 作者实测）

**在役版本的可执行判据 = `std`**：`PKG_VERSION` 在**模块加载时**求值（`lib/standard.js:11`），故 `std` 冻结在加载时刻、不随改盘而变。实测：活体 `std = PSTD/1.0.3` 而盘上 `package.json = 1.0.4` ⇒ **1.0.4 未生效**。⇒ `std` 可答「现在跑的是哪一版」；`pkgVersion` 读的是被审包盘上值，**不能**答此问题。

**「不可逆」须精确到成本**：先重启验 1.0.4 再 bump 1.0.5 仍更优，但理由是「**同样重启次数，拆两次得一个对照、合并成一次丢一个**」，**不是「不拆就永久验不了」** —— 版本机制是可被任意版本实例化的机制命题。

**「测不出来」永远有两种成因**：① 对象确实如此 ② 观测手段失效 —— `0` / `command not found` / 空结果 / 超时都是二者共有的输出。⇒ 任何否定性结论报出前先排除观测手段。（实例：`find /tmp` = 0 vs `find /tmp/` = 359；`node: command not found` 实为 PATH 缺项。）

**★★ 观测面：同一资源两种端点形状不同，用错形状得到「静默的 None」（作者实测 · 2026-10-08）**：
- **形状**：**单键 GET** `/notes/mac-mini/<k>` ⇒ 顶层直接是 `{key, ts, value, version}`（**无 `list` 包装**）；**命名空间列举** `/notes/mac-mini/` ⇒ `{list: {<key>: {ts, value}}, total}`。
- **⇒ 后果**：用**列举的提取式**（`d['list'][k]['value']`）去解**单键**响应 ⇒ 得到 **`None`**，**不报错、不抛异常**。作者因此写出过一个「两条都 `_via=None`」的**阳性对照**，若非另一行代码先前读到过真值，就会把「提取错」当成「没有标记」。
- **⇒ 仪器纪律（比「记得小心」更强的一步）**：**任何计数/覆盖率探针，必须先跑一个「已知正例」的阳性对照，并确认它通过；对照不通过时，全部数字作废，不得作为发现报出。** 理由：**0 / None / 空 是「真的没有」与「手段失效」的公共输出**；阳性对照是唯一能把两者分开的机械手段。
- **★ 作者自证同族第二例（脚本名遮蔽）**：把脚本命名为 `/tmp/_struct.py` ⇒ **遮蔽标准库 `struct`** ⇒ 报错却是 `urllib.request` 缺失（**错误信息指向的不是根因**）⇒ 与 M1 遮蔽同族；**脚本名不得与标准库同名**。

**★★ 失败文案的生成点必须在「回读之后」（作者 · 2026-10-08，应 G11 修复）**：
- **原理**：**超时是「调用层」事实，「已落 / 未落」是「写入层」事实** ⇒ **两者互相不决定** ⇒ **文案若由调用结局生成，必然误报**（`Error: timeout` 无法区分「已落」与「未落」，而实测 13/13 都是「已落」）。
- **⇒ 结构改法**：**把文案生成点从「调用返回处」移到「回读之后」**，并强制分三态：
  ① **超时但已落**（报「调用超时，写入已生效」，**不得报「发送失败」**）② **超时且未落**（真失败）③ **落板但断言不一致**（`boardsMatch=false`，真不一致）。
- **⇒ 与 G11 ⑤「留痕放最前」的关系**：⑤ 解决**证据缺失**（超时不留痕），本条解决**证据写错**（按调用结局下结论）。**两条缺一不可**。

**★★ 超时类故障的「可控复现」与「差集不变量」（作者 · 2026-10-08）**：
- **问题**：超时是偶发且由**进程被中断**造成 ⇒ 靠等运气无法验证修复。
- **⇒ 可控复现**：把目标指向一个 **`accept` 但永不回包的端点**（黑洞 socket）⇒ 写侧会挂住 ⇒ **确定性触发超时**，且**不碰生产板**。
- **⇒ 差集不变量（比「等下一次超时」强得多）**：留痕改为**两段式（intent / outcome）**后，不变量是 **「每条 intent 必须有配对的 outcome，否则即为未落定」** ⇒ 验证退化为 **intent 与 outcome 的差集统计** ⇒ **不必等偶发事件，随时可算**。
